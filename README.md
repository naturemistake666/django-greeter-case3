# Кейс-задача № 3 — Веб-приложение на Django

Учебная практика (технологическая (проектно-технологическая) практика).
Направление 02.03.03, профиль «Разработка программного обеспечения (Full-stack разработка)».

## Условие

Простое веб-приложение: пользователь вводит имя на главной странице и получает
персонализированное приветствие. Имя сохраняется в базе данных через модель
Django с единственным полем `name`. Обрабатывается ошибка пустого поля,
интерфейс стилизован через CSS, приложение защищено от CSRF.

## Стек

Python 3.12, Django 6.1, SQLite (встроенная БД). Внешних JS-фреймворков нет.

## Установка и запуск

```bash
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

Открыть в браузере: `http://127.0.0.1:8000/`

## Тесты

```bash
python manage.py test greeter -v 2
```

13 тестов: модель, форма, представление — включая отдельную проверку, что
запрос без CSRF-токена реально отклоняется сервером с кодом 403.

## Как выполнены требования задания

| Требование | Реализация |
|---|---|
| Форма ввода имени + кнопка Submit | `greeter/templates/greeter/home.html` |
| Модель с единственным полем `name` | `greeter/models.py` — `class Visitor(models.Model): name = ...` |
| Сохранение имени и персонализированное приветствие | `greeter/views.py::home` — `form.save()`, приветствие после сохранения |
| Обработка пустого поля | `blank=False` формы (отклоняет `""` и, из-за автоматического `strip()` у `CharField`, строку из пробелов) + валидатор `validate_not_blank` в модели как страховка на уровне `full_clean()`/админки/`Model.save()` |
| Стилизация CSS | `greeter/static/greeter/style.css` |
| Защита от CSRF | Стандартный `CsrfViewMiddleware` Django (включён по умолчанию) + `{% csrf_token %}` в шаблоне |

## Архитектурные решения

- **Post/Redirect/Get.** После успешного сохранения имени сервер отвечает
  редиректом (`302`), а не сразу рендерит страницу с приветствием. Это
  стандартная защита от повторной отправки формы при обновлении страницы
  (F5) — без неё пользователь мог бы случайно создать несколько одинаковых
  записей.
- **Валидация на уровне модели, а не только формы.** Django-форма отклоняет
  и `""` (через `blank=False`), и строку из одних пробелов — `CharField`
  сам обрезает пробелы (`strip()`) перед проверкой `required`, так что
  `"   "` превращается в `""` и форма выдаёт ту же ошибку "обязательное
  поле". Но это поведение формы, а не модели: если создать объект в обход
  формы (`Model.save()` напрямую, через shell, фикстуру или админку без
  `strip`), пустая по смыслу строка может проскочить. Поэтому в модели
  дополнительно подключён `validate_not_blank` как `validators=[...]` —
  он страхует `full_clean()` независимо от того, как заполняется поле.
- **CSRF проверен, а не просто заявлен.** В тестах есть отдельный сценарий
  (`test_csrf_protection_is_enforced`), который отправляет POST-запрос через
  клиент с `enforce_csrf_checks=True` без токена и убеждается, что сервер
  возвращает `403`, а запись в базу не попадает. Это же подтверждено вручную
  через `curl` на живом dev-сервере.
- **Единственное поле в модели.** По условию задания модель должна содержать
  «только одно поле: name» — служебные поля (например, дата создания записи)
  сознательно не добавлялись, чтобы не выходить за рамки условия.
